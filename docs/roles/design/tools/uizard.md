# Uizard

Uizard 的核心定位一直很清楚：让界面原型变得更像“把想法讲出来”而不是“先学会复杂设计工具”。官方当前最值得关注的是 `Autodesigner 2.0`、`Screenshot Scanner` 和 `Wireframe Scanner` 这三条输入路径。

## 它最适合什么任务

| 任务 | 适合程度 | 原因 |
| --- | --- | --- |
| 早期产品概念探索 | 很高 | 文本、截图、草图都能快速起稿 |
| 多屏原型快速成型 | 高 | `Autodesigner 2.0` 直接出 multi-screen mockups |
| 竞品参考转可编辑草案 | 高 | `Screenshot Scanner` 更适合这种场景 |
| 成熟设计系统长期维护 | 中到低 | 更强在起稿，不在长期源设计治理 |

## 它为什么快

Uizard 官方当前把 AI 路径拆成三种非常直接的入口：

- `Autodesigner 2.0`：从文本生成多屏 mockup
- `Screenshot Scanner`：把截图转成可编辑设计
- `Wireframe Scanner`：把手绘草图转成数字设计

这意味着它很适合在模糊阶段帮助团队先“看见方案”，再决定是否要进入更重的设计系统工具。

## 实战案例

### 案例：创始人和设计师一起做 MVP 原型

1. 创始人先把产品流程和几个关键页面需求写成 prompt。
2. 设计师用 `Autodesigner 2.0` 生成一版多屏原型，先看流程完整性。
3. 发现 onboarding 参考竞品更快，就把竞品截图丢给 `Screenshot Scanner` 做可编辑草案。
4. 在线评审后，对关键页面再做更明确的视觉与交互收敛。
5. 当结构确认了，再把真正要落地的页面迁入 [Figma](/docs/roles/design/tools/figma) 或 [MasterGo](/docs/roles/design/tools/mastergo)。

这类场景里，Uizard 最重要的价值是压缩从“想法”到“可讨论界面”的时间。

## 它更适合什么团队

- 还在找产品方向的创业团队
- 需要快速把想法讲给干系人看的产品/设计组合
- 想先压缩探索成本，再决定是否精修的团队

## 边界与注意事项

- 不要把它误当成长期的设计系统中心。
- 如果你已经有成熟组件库、变量体系和 handoff 流程，最终还是要回到更适合治理的工具。
- 如果你要的是网站信息架构和审批流程，[Relume](/docs/roles/design/tools/relume) 可能比 Uizard 更稳。
