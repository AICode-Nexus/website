# 团队与交付

## 这一类内容解决什么问题

- 个人工程师如何把自己的 AI coding 方法升级为团队可复用流程
- AI coding 进入团队后，review、质量和风险会如何变化
- 哪些指标能说明 AI coding 真正提升了交付
- 团队应该从哪里开始，而不是一上来就大规模推广

## 谁应该先读

- 已经形成个人 workflow 的工程师
- 想把这些做法复制到小团队的人
- 对 review、风险和质量门禁敏感的读者
- 需要向主管或同事解释“为什么这样做”的读者

## 从个人到团队，通常会经历三步

### 第一步：把个人动作显性化

先把你自己的 rules、contract、任务拆解方法写出来。没有显性化，就谈不上团队复用。

### 第二步：把结果接入 review 和验证

AI coding 不是绕开 review，而是让 review 更快发现高风险改动。

### 第三步：再谈指标和治理

团队阶段最关心的是：

- 返工有没有下降
- review 是否更快
- 风险边界是否更清晰

## 常见错误

- 还没有个人稳定方法，就直接推动团队统一采购或统一规范
- 把 AI 当作加速器，却不调整 review 和验证策略
- 只看“写得快不快”，不看返工和 merge 成本
- 试点范围过大，导致无法定位问题来自哪里
