# AI Coding 知识体系总表

## 背景

AI coding 变化快、产品多、名词重复高。如果站点只按工具名组织，内容会很快失控，主要会出现 3 个问题：

- 工具一换代，旧文目录立刻失去稳定性
- 同一主题被拆到多个产品页里，难以形成系统知识
- 新读者无法判断一篇文到底是新闻、教程、选型文还是趋势文

因此，这个站点不按厂商建一级目录，而是按稳定维度建结构：

- 主赛道
- 内容形态
- 受众层级
- 深度阶段

## 结论先行

- 主赛道负责稳定分类，决定一篇文属于哪块长期知识
- 内容形态负责写法，决定这篇文应该怎么写
- 受众层级负责深度，避免所有文都写成同一个难度
- 深度阶段负责阅读顺序，帮助门户页和知识库给出更好的导航

## 适用场景

- 规划站点目录和侧边栏
- 新增选题时判断应该落到哪里
- 判断一篇文应该写成 `guide`、`comparison`、`playbook` 还是 `insight`
- 门户页做卡片聚合和推荐排序

## 核心概念

### 1. 主赛道

主赛道是站点最稳定的一层，短期内不应频繁改动。

| 赛道 | 负责什么 | 典型问题 |
| --- | --- | --- |
| 模型与 Agent | 模型能力、执行方式、记忆和规则 | 哪类模型 / agent 适合哪类任务 |
| IDE 与工具链 | IDE、CLI、review、PR、issue 工具流 | 我应该从哪个入口开始工作 |
| 提示词与工作流 | prompt contract、任务拆解、协作方式 | 我怎样把任务输入变稳定 |
| 团队与交付 | review、质量门禁、指标、风险 | AI coding 怎样进入正式交付 |
| cross-track | 横跨多个赛道的对比、playbook、insight | 需要跨赛道组织的内容 |

### 2. 内容形态

内容形态决定文档写法，而不是决定它的赛道。

| `kind` | 作用 | 写法重点 |
| --- | --- | --- |
| `hub` | 导航页、总览页 | 讲地图、讲顺序、讲入口 |
| `guide` | 基础知识和方法论 | 讲概念、适用场景、推荐做法 |
| `comparison` | 工具或平台对比 | 讲维度、结论、适合谁 |
| `playbook` | 操作型文档 | 讲步骤、合同、验证、失败模式 |
| `insight` | 趋势与阶段判断 | 讲变化、影响、观察点 |

`Daily Brief` 不放在 docs 里，它属于 `/blog`，负责时效更新。

### 3. 受众层级

| `audience` | 适合谁 | 语气与密度 |
| --- | --- | --- |
| `individual` | 个人工程师 | 先讲动作和决策 |
| `mixed` | 个人与团队都适用 | 兼顾方法与治理 |
| `advanced` | 高控制、强配置、平台治理场景 | 更强调边界与 tradeoff |

### 4. 深度阶段

| `stage` | 适合什么时候读 |
| --- | --- |
| `starter` | 第一次建立认知与路线 |
| `intermediate` | 已经开始实战，需要提高稳定性 |
| `advanced` | 进入治理、组合和高复杂度工作流 |

## 推荐做法

### 先分赛道，再分写法

新增内容时，先问：

1. 这篇文长期属于哪个赛道
2. 它是导航、教程、对比、操作手册还是趋势判断
3. 它更应该面向谁
4. 它放在 `starter`、`intermediate` 还是 `advanced`

如果顺序反过来，通常会出现“写着写着越界”的问题。

### 所有文档都要有元数据

当前站点统一使用这些 frontmatter 字段：

- `track`
- `kind`
- `audience`
- `stage`
- `featured`

这不是为了形式统一，而是为了给门户页、筛选聚合、后续自动化推荐提供稳定信号。

### 一篇文只解决一种主要问题

高质量知识库的关键不是内容多，而是边界清楚。

例如：

- “GitHub Copilot vs VS Code Agent vs Codex” 应该是 `comparison`
- “个人工程师栈搭建” 应该是 `playbook`
- “2026 年 3 月月度简报” 应该是 `insight`

不要把新闻、教程、评测、操作指南混在一篇文里。

## 常见错误

### 错误 1：用产品名做一级目录

后果：目录会跟着厂商版本震荡，长期结构不稳定。

修正：把产品名放进对比文、赛道文和趋势文，而不是把产品名当站点骨架。

### 错误 2：把 Daily Brief 当知识库文档

后果：站点很快充满时效性文本，但长期知识很少。

修正：Daily Brief 留在 `/blog`，长期判断沉淀进 `/docs`。

### 错误 3：所有文章都面向“所有人”

后果：新手觉得太难，进阶读者觉得太浅。

修正：明确 `audience` 和 `stage`，让导航系统有意义。

### 错误 4：没有跨赛道容器

后果：对比文、playbook、insight 被硬塞进单一赛道。

修正：保留 `cross-track`，专门容纳需要跨赛道组织的内容。

## 分类决策表

当你准备新增一篇文时，可以先用这个快速判断：

| 你想写什么 | 应放哪里 |
| --- | --- |
| 某个工具或平台怎么选 | `/docs/comparisons` |
| 一套可执行步骤 | `/docs/playbooks` |
| 某条长期趋势判断 | `/docs/insights` |
| 某赛道的基础认知 | 对应 `/docs/tracks/...` |
| 新近发生的变化 | `/blog` |
